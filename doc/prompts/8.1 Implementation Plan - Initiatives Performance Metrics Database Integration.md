# Implementation Plan - Initiatives Performance Metrics Database Integration

## 1. Overview & Goal
The section `#initiativesDashboardCard` ("Initiatives Performance Metrics") currently displays hardcoded mock data defined in `index.js` (`projectPerformanceMetrics`) and static aggregate metrics (`13`, `99.8%`, `45k+`, `100%`) in `index.html`.
The goal is to load real performance telemetry data dynamically from the Supabase database (`public.project_metrics`), update individual project telemetry cards, dynamically recalculate or display aggregate metrics, and seamlessly fall back to client defaults if Supabase is offline or not yet configured.

---

## 2. Technical Architecture & Data Strategy

### 2.1 Schema & Remote State
- The database schema is defined in [`doc/db/project_metrics_schema.sql`](../db/project_metrics_schema.sql).
- Remote table: `public.project_metrics`
  - `id`: UUID (Primary Key)
  - `project_name`: TEXT (Unique)
  - `category`: TEXT
  - `status`: TEXT
  - `status_type`: TEXT (`operational`, `beta`, `dev`)
  - `health_score`: INTEGER (0 to 100)
  - `summary`: TEXT
  - `kpis`: JSONB array of objects (`[{"label": "...", "val": "..."}]` or `[{"label": "...", "value": "...", "trend": "..."}]`)
- RLS Policy: Public read-only (`FOR SELECT USING (true)`). Writes restricted to `service_role`.

### 2.2 Client Ingestion & Normalization
- In `index.js`, an active cache object `loadedProjectMetrics` will store normalized telemetry indexed by project name:
  - Supports both `kpi.val` and `kpi.value`.
  - Normalizes `statusType`: `operational` -> `online`, `beta` -> `beta`, `dev` -> `dev`.
  - Normalizes `healthScore`: ensures numeric value formatted with 1 decimal or integer.
- The routine `fetchProjectMetricsFromDB()`:
  - Checks if `supabaseClient` is initialized.
  - Queries `supabaseClient.from('project_metrics').select('*')`.
  - If successful and rows exist, updates `loadedProjectMetrics`, re-renders the metrics grid via `renderProjectMetricsDashboard()`, and updates aggregate stats in `#initiativesDashboardCard`.
  - If the database query fails (e.g. table not yet run or network offline), catches the error quietly without throwing, keeping the fallback static metrics active.

### 2.3 Aggregate Telemetry Calculation
- Dynamic aggregate computation based on loaded metrics:
  - **Active Initiatives**: Dynamic count of known projects (`primaryProjects.length` or loaded items).
  - **System Health**: Average `health_score` across all projects (e.g. `98.2%`).
  - **Monthly Impact** & **Open Ecosystem**: Populated dynamically from aggregated KPIs or graceful live values.

### 2.4 HTML Enhancements
- In [`index.html`](../../index.html#L627-L644):
  - Assign explicit IDs to the aggregate statistic numbers:
    - `#aggActiveCount`: Active Initiatives count
    - `#aggSystemHealth`: System Health percentage
    - `#aggMonthlyImpact`: Monthly Impact count
    - `#aggOpenEco`: Open Ecosystem percentage
